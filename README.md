# CyberSolutions — Security Platform

> Proof, not noise.

Application security for TypeScript/Node web applications that **confirms vulnerabilities
and verifies fixes**, instead of handing you a list of maybes.

Start with [`docs/architecture.md`](docs/architecture.md) — what the system is, how the
pieces fit, and the invariants CI enforces.

## The loop

```
DETECT  →  EXPLAIN  →  FIX  →  VERIFY  →  MONITOR
```

## The three constraints that are not negotiable

1. **`confidence: 'confirmed'` may only be set by the Verification Engine.** No rule may
   assert exploitability. Enforced by `assertRuleEmittableConfidence()`.
2. **Only proven findings fail a build.** See `DEFAULT_FAIL_POLICY`. This is the trust
   contract, not a tunable default.
3. **The verification safety gate is built and adversarially tested before a single real
   request is sent.** Build order items 52–54, in that order.

## Naming

| Surface | Value | Status |
|---|---|---|
| npm scope | `@security-doctor` | **register the org** (free public plan) |
| GitHub org | `security-doctor` | confirmed available at time of writing |
| CLI binary | `security-doctor` | the `bin` name, independent of the package name |
| CLI package | `@security-doctor/cli` | `npx @security-doctor/cli scan` |
| Domain | `security-doctor.dev` | **unconfirmed — check before first publish** |

Three things to settle before the first `npm publish`:

- **Publish something real to the org soon.** npm's terms forbid registering an org or
  package name purely to reserve it, and an org with no packages "within reasonable
  timeframes" counts as squatting. `@security-doctor/finding-model@0.0.1` is a genuine
  package and can ship today. Never publish placeholder or typosquat packages — that is
  what npm removes accounts for.
- **The JSON Schema `$id` URLs are published identifiers.** They point at
  `security-doctor.dev`. Once anything validates against them, changing them is a
  breaking change. Own the domain first.
- **The unscoped `security-doctor` package name is taken** by an unrelated solo project
  (`nkd52`, ~26 downloads/month). So PRD §15.1's `npx security-doctor scan` is currently
  `npx @security-doctor/cli scan`. A polite transfer request is worth one email — npm
  will not force a transfer, but voluntary handovers are routine. If it lands, the
  unscoped name becomes a thin alias and nothing else changes.

## Publishing

**You cannot publish from your laptop.** Both contract packages set
`publishConfig.provenance: true`, and npm provenance is only generated by GitHub Actions
or GitLab CI on a cloud-hosted runner — local publishing with provenance is explicitly
unsupported. That is deliberate (PRD §13.2: a security vendor's supply chain is the
product), but it means the order below is not optional.

1. **Register the npm org** `security-doctor` — free "Unlimited public packages" plan.
2. **Create the GitHub org and repo at exactly `security-doctor/platform`.** Provenance
   requires the `repository` field to match the publishing source *case-sensitively*, and
   both packages now point at `git+https://github.com/security-doctor/platform.git`. A
   different repo path means provenance fails at publish time.
3. **Configure the `npm-publish` GitHub Environment.**
   - Add `NPM_TOKEN` as an **environment** secret (not a repository secret) — a granular
     access token, read+write, scoped to `@security-doctor` only. Environment-scoping
     means only jobs that name this environment can read it.
   - Set **Deployment branches and tags** to `main` only, so a release can never be
     triggered from a feature branch.
   - **Required reviewers will not appear while this repo is private.** GitHub only
     offers deployment protection rules on public repositories for Free/Pro/Team plans.
     That is fine for now: with a team of one, self-approval is theatre. Turn it on when
     the repo goes public or a second engineer joins — it is listed in PRD §13.4 as the
     mitigation for release-pipeline compromise, and it stops being optional then.

   `release.yml` already requests `id-token: write` and sets `NPM_CONFIG_PROVENANCE`.
4. **Merge the version PR** that changesets opens. `.changeset/initial-contract-packages.md`
   takes both packages to `0.1.0`.

**After the first publish, remove the npm token.** npm trusted publishing (OIDC) lets
GitHub Actions publish without any long-lived credential, and still generates provenance.
It is configured per package on npmjs.com once the package exists, so it cannot be used
for the very first publish. As soon as both packages are live: configure a trusted
publisher on each (Settings -> Trusted Publisher -> GitHub Actions, workflow
`release.yml`), then delete `NODE_AUTH_TOKEN` from `release.yml` and delete the
`NPM_TOKEN` secret. The release job already runs Node 22 for this.

Already done: the Apache-2.0 text is in place at the repo root and in both packages, and
every third-party action is pinned by commit SHA. To bump a pin, re-resolve it with
`git ls-remote --tags --refs https://github.com/<owner>/<repo>` — never copy a SHA from
memory or from a blog post.

After that, `@security-doctor/finding-model` and `@security-doctor/evidence-schema` are
live with verified provenance — and the org is in genuine use rather than parked, which
is what npm's terms require.

## This repository is public

Two standing rules follow from that:

1. **`docs/PRD.md` is gitignored and must stay that way.** It is the commercial strategy —
   ICP, competitive analysis, pricing direction, the risk register, hiring. It lives on
   maintainers' machines and in the team's document store. Contributors get
   `docs/architecture.md`.
2. **Vulnerability reports come through GitHub private advisories** (see `SECURITY.md`),
   not an email address. Enable *Settings → Security → Private vulnerability reporting*.
